# Decision Log

Problem #4 — policy agreement extraction and eligibility. Run: `npm start`. Eval: `npm run eval`, output committed as [`EVAL_RESULTS.md`](./EVAL_RESULTS.md). Build history in [`DECISION_CHRONOLOGY.md`](./DECISION_CHRONOLOGY.md).

**1. Why this process, which shape?** Problem #4 taken directly. Chosen because it maps onto the claims-eligibility pipeline we discussed at interview. The invented situation (HCRS-1) is a fictional home-cover redress scheme: six gates in order — cover window → early-cancellation carve-out → prior ruling → no-commission → de minimis → qualifies on discretion (B1) or a ≥35% commission ratio (B2). Four outcomes, not three: *escalate* and *insufficient-data* have different causes and different remedies.

**2. How did I scope it? What did I cut?** Over-specced first: XState machine per document, SQLite claim-queue, ingester/consumer split, four layers, 25 files. Stopped **before writing implementation code**, audited it against what the brief actually grades, and threw most of it away. Cut: agent frameworks, XState, SQLite and the whole queue mechanism, PDF/OCR, native provider SDKs, HTTP ingestion, field-level provenance. What shipped is five files, ~720 lines. Node/TS over Python because it mirrors your stack and I'm faster in it. **On the clock:** build took ~90 minutes including plan and initial scaffold, review and debug ~30 mins, write-up ~30 mins. Overall 2h 30mins. Had I built the initial spec, I’d be well over 4 hours — hence I'd rather show the process and judgement that killed it.

**3. Where a model, where not, and at 10k/month?** Models do extraction only, twice. The decision is a pure function (`rules.ts`) receiving validated fields and never document text — so a verdict is byte-identical and re-derivable — this is the prompt injection defence. Reconciliation, costing and tracing are arithmetic. Measured **$8.88/10k dual-pass**, $5.03 single. Caveats: that's extraction over `.txt` only, OCR would dominate on real packs. Cheap model wasn’t cheap: GLM priced 4.8× below Luna per output token but emitted **4.9× more tokens** (24,682 vs 5,086), so the passes cost nearly the same.

**4. Two configurations, metric, winner.** **A:** single-pass, Luna alone. **B:** dual-pass — both models extract independently, rules run on each, disagreement escalates. Both scored from the *same extraction pair*, so the only variable is reconciliation, not extraction noise.

Reconciliation never invents a better verdict — it only converts a committed verdict into an escalation. Under `verdict == gold` accuracy every escalation counts as a miss, so dual-pass is *arithmetically incapable* of winning; the metric would be scoring willingness to guess. So: **harmful-error rate** (auto-decided ELIGIBLE↔NOT_ELIGIBLE the wrong way) against **automation rate** measures the trade off.

| | A single | B dual |
|---|---|---|
| Harmful errors | 4/20 (20%) | **3/20 (15%)** |
| Soft errors | 3/20 | **2/20** |
| Automation rate | **100%** | 85% |
| Precision when committing | 65.0% | **70.6%** |
| Cost /10k | **$5.03** | $8.88 |

Two escalations caught wrong verdicts (hcrs-01, hcrs-20); one escalated where the answer was already correct (hcrs-12). **B wins**: ~3 escalations per harmful error avoided, ≈£5 of handler time each, against a wrongly-pursued redress claim costing far more. **Neither is deployable** — 15% harmful is a triage assistant, not automation — **three of four harmful errors survived reconciliation** because both models failed identically.

**5. Where it breaks.** *At volume:* documents run in batches behind a `Promise.all` barrier, so one slow document stalls its batch — hcrs-18 did exactly that mid-run. Worst case 7.6 min/document, no backpressure, no DLQ, no idempotent claim. *Under unplanted input:* the design is structurally immune to the planted prompt injection but the attack that works misstates a **value**: hcrs-14 states commission twice (£62 true, £620 decoy), both models took the decoy turning an exclusion into ELIGIBLE. Schema passes, models agree, no rule trips. Underneath sits the assumption dual-pass rests on — independent failure. Dual-pass only works if the two models make _different_ mistakes.

**6. What production needs next.** (i) Field-level provenance — the source span per value; the direct answer to hcrs-14, and the cut I most regret. More generally extraction needs to be fixed before scaling (ii) Real orchestration — SQS/Step Functions, idempotent claim, DLQ, backpressure — flow control/rate-limiting consumers. (iv) Gold labels from real operational records instead of synthetic (v) Rules as versioned data with `ruleset_version` stamped on decisions. (vi) Split the escalation queue — "disagreed" and "one pass failed" with different handlers.

AI-assisted development.** Three assistants, three roles. **Claude (design):** Accepted Node/TS over Python (it corrected a wrong assumption I'd stated about the stack) and the pure decision layer; rejected its one-shot batching, which had no idempotency story (for the initial spec), and authored specs.json for the synthetic data. **Gemini (data, scaffold — fast):** ran the audit to kill most of the initial spec and reduce it to min viable, authored all 20 synthetic data docs, scaffolded the source. **Claude Code (review):** a fresh-context pass against the invariants found six defects, five silent (D-13→D-19): dual-pass existed only in the eval, so `ESCALATE_HUMAN` was unreachable in production; the gold-set join never matched, so every accuracy figure would have been vacuous; cost was wrong by 1000×; the injection had never been planted. Building with assistants got me a pipeline in 90 minutes; adversarially reviewing with one is what made it true.

**Position on PII.** Corpus is entirely synthetic — invented firms, people and postcodes. The extraction schema is a **whitelist, not a filter**: names and addresses in the source are never extracted and cannot reach a decision or a trace. Only `provider_name` and `policy_reference` persist, both institutional. Raw text is discarded after extraction — checkable in the import graph, not promised in a prompt — so a trace is safe to hand an auditor. In production the position must be stronger, because full text would leave the building for a third-party API: zero-retention or BYOK, redaction before the call, a Data Processing Agreement covering the provider, or on-prem inference. The whitelist limits what is *stored*, not what is *transmitted*.

**With more time:** model selection and prompt iteration first — by far the lowest hanging fruit. Then field provenance, doesn’t fix extraction but makes contradictions visible which could remove one of four harmful errors and a known failure model. Then address the synthetic data and replace the gold set from real operational records — fine tune on this. Only when harmful errors are reduced to an acceptable level, then address scale: backpressure, DLQ, idempotency etc. Done this way because the current harmful error rate is 15%, scaling would just make the system produce wrong answers faster.
